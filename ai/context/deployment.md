## Database

| environment | /api/health reports |
|---|---|
| stage | database reachable, schema migrated |
| prod | database reachable, schema migrated |

Each environment is its own Supabase project (`prisma-blog-stage`,
`prisma-blog-prod`), reached only through the Worker's Hyperdrive binding. The
schema is db-migrate's (`packages/db/src/migrations`): the posts, and
next-auth's users, GitHub accounts, sessions and verification tokens, as
`apps/web/prisma/schema.prisma` declares them, and the secret next-auth signs
its cookies with, generated once per database into `app_private.secrets`.
Every table in `public` has row-level security and no policy, and
`app_private` is not a schema the Data API exposes, so Supabase's Data API
serves none of it — not a post, not a session token, not an OAuth token.

## Sign-in

| environment | GitHub sign-in (`/api/auth/providers`) |
|---|---|
| stage | not connected — the blog serves its feed and posts signed-out |
| prod | not connected — the blog serves its feed and posts signed-out |

GitHub sign-in is the owner's to connect: a GitHub OAuth App per
environment, its id and secret stored as `GITHUB_ID` and
`GITHUB_SECRET`, then a redeploy (README, "Connecting GitHub sign-in").
Until then the blog has no writers: the feed and every published post read
signed out, and "Log in" says how to connect GitHub.

## Secrets (names only)

| secret | where | what it is |
|---|---|---|
| `CLOUDFLARE_API_TOKEN` | the workspace | BROKERED from its Cloudflare connection (`workers-deploy`): deploys the app's Worker |
| `CLOUDFLARE_HYPERDRIVE_TOKEN` | the workspace | BROKERED (`hyperdrive-edit`): applies the Hyperdrive config — the deploy token cannot touch Hyperdrive |
| `CLOUDFLARE_ACCOUNT_ID` | the workspace | the Cloudflare connection's account id — a fact, not a credential |
| `SUPABASE_ACCESS_TOKEN` | the workspace | BROKERED from its Supabase connection (`management-access`): creates the project and runs the migrations |
| `SUPABASE_ORG_ID` | the workspace | the Supabase connection's organization id — a fact, not a credential |
| `SUPABASE_PROJECT_REF`, `SUPABASE_DB_PASSWORD`, `SUPABASE_DB_URL` | `prisma-blog` on stage and on prod | written by the Supabase root's apply: the project's ref, its database password and its connection URL, read by Hyperdrive and the migrations |
| `WIRING_CLOUDFLARE_HYPERDRIVE` | `prisma-blog` on stage and on prod | written by the Hyperdrive root's apply: the config's id and name, not a credential |
| `GITHUB_ID`, `GITHUB_SECRET` | `prisma-blog` on stage and on prod, once the owner sets them | the GitHub OAuth App's client id and secret, pushed to the Worker as Worker secrets at deploy — optional: without them the blog has no sign-in |
| `SECRET` | `prisma-blog` on stage and on prod, only if the owner sets one | the secret next-auth signs its cookies with, pushed to the Worker as a Worker secret; unset, the Worker uses the one its database generated |

Brokered secrets are minted per run, so no long-lived value is at rest. The
cookie secret is generated inside each environment's database by the
migrations and never leaves it except to the Worker, which reads it through
its Hyperdrive binding. Sessions themselves are rows in the `sessions`
table. What the workspace holds right now (every secret by
name, and its integrations and their health) is on the console's Secrets and
Integrations pages for `org_eefc498630dc41058bcd9875abc4efed`.
